# Connect the shared service

The application works locally without these values. The shared features stay visibly disconnected until configured. Use a Supabase project owned by the app owner. Do not paste secret keys in chat or commit them.

1. Create a Supabase project in an appropriate region. Apply `supabase/migrations/202610030001_workspace.sql` using its SQL editor. The migration enables RLS and uses narrow RPCs for all mutations. It is intended for a new schema; do not rerun it over an existing installation without a migration review.
2. Enable email authentication. Set Site URL to `https://cityrelay.vercel.app` and allow `https://cityrelay.vercel.app/account` (including invite query parameters). Configure a production email sender before inviting real users. Local testing can allow `http://127.0.0.1:4182/account`.
3. Add `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` to Vercel and the local `.env.local`. These public project values may be included in browser code; database policies provide authorization. Never place a service-role key in a `VITE_` variable.
4. Redeploy. Test sign-in with two separate accounts, then create a shared copy from Account & backup. Copying is explicit, scoped to one municipality, and excludes local practice reports. Invite the second account using its exact email and check that a third account has no access.
5. Enable resident intake from the owner account, name the receiving team, and test its `/resident/:id` link in an independent browser. Save the full receipt; verify that intake approval changes its status. All reports initially require human intake review. Current intake is bounded to 200 submissions per workspace per day; add a production abuse-control provider before an open public campaign.
6. Background checks: configure `SUPABASE_SERVICE_ROLE_KEY` and a strong `CRON_SECRET` as server-only Vercel variables. The daily cron at 06:00 UTC checks the five approved pages for enabled workspaces; no AI calls or emails are made. It processes up to 100 workspaces per run. Increase capacity with pagination when needed. Daily scheduling respects the Hobby cadence; a tighter schedule needs an appropriate hosting plan. Browser checks remain available every 15 minutes while visible.
7. Optional live AI: set server-only `OPENAI_API_KEY` and `OPENAI_MODEL`. Public research requires a signed-in shared workspace, per-run consent and an atomic database allowance of three attempts per account per UTC day. Failed attempts count toward the limit. Set the provider project spending budget before enabling. No provider key is sent to the client. The workspace remains usable without AI.

Release verification still requires real email delivery, actual deployed RLS, two-account save conflicts, anonymous report delivery, scheduled execution and a consented AI run. Embedded PostgreSQL tests verify the migration logic; they do not substitute for that deployment check.

Municipal affiliation is self-declared, not independently certified. Owner publication of a reporting form must not be presented as official accreditation. Production privacy operations (retention, access requests, account deletion, incident response and organisational verification) need the operating organisation's policy and owner decisions.
